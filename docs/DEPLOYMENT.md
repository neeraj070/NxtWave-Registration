# Deployment preparation

## Current status

This project has **not** been deployed. There is no public URL. The workspace is not currently a Git repository, so Render cannot build it until the project is committed to a Git provider repository and connected by the owner. No hosting account or external service was modified during this preparation.

## Recommended host: Render Web Service with a persistent disk

Render is a simple fit for the current single-process Node.js + Express + SQLite app: it supports a native Node runtime, a repository-based Blueprint, and a disk mounted where this app stores its database. This option requires a paid compute plan for the persistent disk; Render's free web services have ephemeral filesystems and would lose a local SQLite database on restart or redeploy. A mounted disk is available to one service instance, so keep the service at one instance. See [Render persistent disks](https://render.com/docs/disks), [Render free service limitations](https://render.com/docs/free), and the [Blueprint reference](https://render.com/docs/blueprint-spec).

## Prepared configuration

`render.yaml` defines a Node web service with `npm ci`, `npm start`, `/health` health checks, and auto-deploy disabled. It mounts a 1 GB disk at `/opt/render/project/src/data`; `DATABASE_PATH` points the SQLite file into that mount. `APP_URL` references Render's generated external URL. `SESSION_SECRET` is generated by Render, and `ADMIN_PASSWORD` is prompted as a secret during initial Blueprint setup. Secret values are not stored in this repository.

The Render disk path and secret fields follow Render's current Blueprint documentation. The Blueprint has not been submitted to Render's validation endpoint or deployed; those checks require an owner-controlled Git repository and Render account.

## Owner steps when ready

1. Review the cost of a paid Node web service with a persistent disk in the Render dashboard. A free web service cannot persist this SQLite database.
2. Create a Git repository for this project and push the reviewed files. This workspace currently has no `.git` directory or configured remote.
3. In Render, create a Blueprint instance for that repository and review the proposed `campusai-growth-hub` service and disk before approving any service creation. The Blueprint sets `autoDeployTrigger: off`; later changes will not deploy automatically.
4. Enter a new, unique `ADMIN_PASSWORD` in Render's secret prompt. Keep the generated `SESSION_SECRET`; do not copy the local `.env` values into the public service. Render supplies `APP_URL` from the generated HTTPS service URL and `PORT` at runtime.
5. After the owner explicitly creates the service, verify `/health`, `/register`, `/admin`, login, demo registration, duplicate handling, referral attribution, and database persistence across a controlled restart. Only then publish the URL.

## Public exposure limits

This prototype is suitable for an owner-controlled product demonstration after deployment checks, not for collecting real student data publicly. Before real registrations, replace Express's in-memory session store with a persistent store, add CSRF protection and security headers, review consent and retention, define database backups and migration handling, and review the admin surface. A mounted SQLite disk also prevents scaling this deployment horizontally; move to a managed database and shared session storage if that becomes necessary.
